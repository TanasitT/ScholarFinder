# ScholarFinder

Finds qualified peer-review candidate scholars for a given paper (title/abstract/keywords), enforcing strict, deterministic eligibility rules, and persists results so past research is reused across papers.

## Layout

Monorepo split into `backend/` (Python — CLI, pipeline, rule engine, SQLite storage, HTTP API, chatbot; fully implemented) and `frontend/` (React + Vite SPA calling the backend API; implemented for search + browse, dev-mode only). Backend paths below are relative to `backend/` unless stated otherwise; frontend paths relative to `frontend/`.

## Architecture

- **Hard eligibility rules are never decided by an LLM.** `src/reviewerfinder/rules/filters.py` and `rules/zones.py` are pure, deterministic Python functions — every pass/fail decision is auditable and stores its reasons. The chatbot (`chatbot/tools.py::check_scholar_fit`) calls these same functions and is instructed (via its system prompt) to report the verdict verbatim rather than re-deriving eligibility itself.
- **Data sources**: OpenAlex (primary — topical search + author metrics + open-access links, `clients/openalex.py`) and Semantic Scholar (secondary cross-check + homepage email-hunting lead, `clients/semantic_scholar.py`). Google Scholar/Scopus are not scraped/queried automatically; convenience search-URLs are generated instead, since Scholar blocks scraping and Scopus needs paid institutional access.
- **Storage**: SQLite (`data/reviewerfinder.db`), not JSON files — filtering/staleness/join queries are inherently relational. Schema in `db/schema.sql`, access via `db/repository.py`.
- **Keyword-set decomposition**: every search first calls `discovery/keyword_summarizer.py::generate_keyword_sets()` (a local **Ollama** model via a plain HTTP call to `{OLLAMA_BASE_URL}/api/chat`, default `llama3.1`) to decompose the paper's title/abstract/keywords into exactly 5 distinct 3-keyword search angles, persisted as `keyword_sets` rows. This means Ollama (the app/service, plus the configured model pulled locally) must be running for `search` to work — `api/deps.py::check_ollama_reachable()` fails a search request fast with a clear 503 if it isn't, before any OpenAlex budget is spent. Malformed/wrong-shaped LLM output raises `RuntimeError` rather than silently proceeding — unlike enrichment or email-hunting, there's nothing to search for without valid keyword sets, so this fails loudly. The LLM only ever shapes *what gets searched for*; it never touches eligibility.
- **Pipeline**: `pipeline.py::run_search()` creates one parent `Paper`, generates its 5 keyword sets, then runs `_run_for_keyword_set()` once per set — each an independent full pass: candidate discovery (`discovery/candidate_finder.py`, using that set's own 3 keywords, not the paper's original ones) → enrichment (`discovery/enrichment.py`) → **core-rule filtering** (zone/institution/pubs/h-index, `rules/filters.py` with `check_email=False`) → **email hunt** for core-rule passers only (`discovery/email_hunter.py`, scrapes OA papers then Semantic Scholar homepage — never constructs/guesses emails) → **final filtering** (same `passes_all_hard_rules()` with `check_email=True`) → ranking (`rules/ranking.py`, ordering only, never filtering) → persistence, keyed by `(paper_id, keyword_set_id, scholar_id)`. Every ranked passer is persisted; only the top `results_per_set` (default 5) come back in the result object.
- **HTTP API** (`api/`): a thin FastAPI layer over the same `pipeline.run_search()` and `db/repository.py` — no business logic lives here. `Paper`/`Scholar`/`KeywordSet` from `models.py` are reused directly as response models. Every route/repository dependency goes through `api/deps.py::get_db_path()` (itself overridable) rather than importing `config.settings.DB_PATH` directly — needed so tests can't accidentally write to the real database (see Conventions below for the bug this fixed). Run via `reviewerfinder.cli serve`; the React frontend talks to it through Vite's dev proxy, so no CORS middleware is configured.
- **`POST /api/papers/search` is asynchronous**: a real search can take minutes (5 keyword sets × many sequential external HTTP calls each for enrichment/email-hunting), so this endpoint starts the search on a background thread and returns a job id immediately (`api/jobs.py`, in-memory only — jobs vanish on server restart). Poll `GET /api/papers/search/{job_id}` for status; `pipeline.run_search()`'s optional `on_progress(stage, done, total)` callback drives the reported progress, with `stage` either `"generating_keywords"` or `"set_<N>_<phase>"` for N in 1..5. The frontend's `SearchPage`/`SearchProgress` parse this to show a real per-set progress bar.

## Build phases

1. **Phase 1 (done)**: core pipeline, no email discovery, no chatbot.
2. **Phase 2 (done)**: email discovery via scraping (`discovery/email_hunter.py`, including PDF text extraction via `pypdf` for PDF-only open-access papers) — never construct/guess emails from name+domain patterns. Verification is a no-op (`unverified`, `clients/email_verifier.py`) until a paid provider is configured.
3. **Phase 3 (done)**: LangChain chatbot (`chatbot/`) — `langchain.agents.create_agent` with a local Ollama model via `langchain_ollama.ChatOllama` (`chatbot/agent.py`; originally Claude/`ChatAnthropic`, switched to match `search`'s zero-paid-API-key posture — see Conventions), five tools over the stored data (`chatbot/tools.py`: `lookup_scholar`, `lookup_paper`, `check_scholar_fit`, `list_top_candidates`, `search_new_candidates`), and a `SqliteSaver` checkpointer for cross-session memory (`chatbot/session.py`, `data/chat_sessions.db` — kept separate from `reviewerfinder.db`'s domain tables). Run via `reviewerfinder.cli chat`. `search_new_candidates` (which spends OpenAlex budget) is only soft-gated — the system prompt tells the model to ask for confirmation first, but nothing programmatically blocks the tool call; harden with LangGraph's `interrupt_before` later if that's not sufficient. Local models are less reliable at consistent tool-calling than Claude was — worth knowing if the chatbot's behavior seems inconsistent.
4. **Frontend (done, search + browse)**: React + Vite SPA in `frontend/` — a new-search form (with a confirm step before spending OpenAlex budget), a past-papers list, a paper detail view with ranked matches, and a scholar detail view. Talks to the new `backend/src/reviewerfinder/api/` FastAPI layer. Dev-mode only (`vite dev` + `uvicorn --reload`) — no production build/serving story yet, no auth, and the chatbot is not in the browser (still CLI-only).
5. **Keyword-set decomposition (done)**: every `search` (CLI, API, chatbot's `search_new_candidates`) now decomposes the paper into 5 distinct 3-keyword angles via a local Ollama model before searching, running each independently and returning up to 5 scholars per angle rather than one flat ranked list. See the Architecture section above for the mechanics.

## Commands

All run from inside `backend/`:

```
cd backend
python -m pip install -e ".[dev,chatbot,api]"  # install deps incl. LangChain + FastAPI (venv recommended)
pytest                                    # run unit + integration tests
python -m reviewerfinder.cli search --title "..." --abstract "..." --keywords "a,b,c"
python -m reviewerfinder.cli refresh      # bulk re-check stale scholars
python -m reviewerfinder.cli chat         # interactive chatbot
python -m reviewerfinder.cli serve        # HTTP API on :8000, for the frontend
```

Requires `backend/.env` (copy from `backend/.env.example`) with `OPENALEX_API_KEY` for `search`/`refresh`, and a running local **Ollama** (ollama.com, plus `ollama pull llama3.1` or whatever `OLLAMA_MODEL` is set to) for `search`'s keyword-set decomposition and for `chat`'s model — no paid API key/billing needed anywhere in this project. The API's browse-only endpoints (list/detail) work without any of the above; only `/api/papers/search` needs `OPENALEX_API_KEY` + a reachable Ollama.

Frontend (separate terminal, from `frontend/`):
```
cd frontend
npm install
npm run dev    # :5173, proxies /api to :8000 -- run `reviewerfinder serve` first
```

## Conventions

- Country-zone data lives in `data/seed/zones.yaml` as *data*; enforcement (including the unconditional Egypt/Saudi Arabia exclusion) stays in `rules/zones.py` code, not the yaml, so editing the yaml alone can't accidentally allow an excluded country. **Quote every country code in the yaml** — YAML 1.1's boolean resolver silently turns bare `NO` (Norway) into `False`.
- Every evaluated candidate (pass or fail) is persisted to `paper_scholar_matches` with its `fail_reasons_json`, so rejections stay explainable later, not just successes.
- Tests: unit tests are pure/offline (`tests/unit/`); integration tests mock `requests.Session.get` against recorded JSON fixtures (`tests/integration/`, `tests/fixtures/`) — no live API calls in the test suite.
- `config/settings.py`'s `PROJECT_ROOT` is `backend/` (two levels up from the settings file) — data/db paths and `.env` loading are all relative to `backend/`, not the repo root. Commands must be run with `backend/` as the working directory.
- `discovery/enrichment.py::scholar_from_openalex_author()` always builds a brand-new `Scholar` with email fields unset — any code path that rebuilds a scholar from a fresh OpenAlex fetch (staleness refresh in `pipeline.py`, `cli.py refresh`, `chatbot/tools.py::check_scholar_fit`) must call `enrichment.carry_over_email(new, old)` afterward, or a stats-only refresh silently wipes previously-discovered email data.
- Every `api/` route and dependency must obtain the database path via `api/deps.py::get_db_path()` (a `Depends()`-injected, test-overridable function), never by importing `config.settings.DB_PATH` directly in a route body. An earlier version of `POST /api/papers/search` did the latter and its own test silently wrote fixture data into the real production database — caught by noticing unexpected rows show up via a manual `curl` check, not by the test itself (the test passed either way).
- `discovery/email_hunter.py::_pick_best_email()` requires the scholar's own name to appear in an email's local-part before attributing it to them — a scraped page/PDF often lists several people's emails (co-authors, department staff), and picking "the first non-generic-looking one" without a name check will silently attribute a stranger's email to the wrong scholar. Found via a real live search that returned `morgan.lee@example.org` for a scholar named "Taylor S. Sample." No name match → reported as not-found, never a guess.
- `db/repository.py::ScholarRepository.upsert()` retries without `semantic_scholar_id` on a `sqlite3.IntegrityError` for that column — `cross_check_with_semantic_scholar()`'s fuzzy name-based matching can occasionally resolve two distinct OpenAlex scholars to the same Semantic Scholar author id, and the `UNIQUE` constraint would otherwise crash the entire enclosing search (this happened on a real ~130-candidate search, killing everything already found). `pipeline.py`'s per-candidate enrichment loop also has a broad `try/except` for the same reason — one bad candidate must never sink a multi-minute batch.
- `paper_scholar_matches`'s uniqueness key is `(paper_id, keyword_set_id, scholar_id)`, not just `(paper_id, scholar_id)` — a scholar can legitimately surface under more than one keyword set for the same paper. `MatchRepository.record_match()`'s `keyword_set_id` param must be set for every real call site; SQL treats `NULL != NULL`, so two calls with no `keyword_set_id` are **not** deduplicated by the `ON CONFLICT` upsert (see the regression test documenting this in `tests/unit/test_repository.py`) — this is only safe because every current caller always supplies one.
- There is no schema migration system — `db/schema.sql` only runs `CREATE TABLE IF NOT EXISTS`, so it never alters an already-existing table. Any schema change (new column, changed constraint) requires deleting the local `data/reviewerfinder.db` and letting `init_db()` recreate it from scratch. Fine for a local single-user dev tool; would need real migrations before any shared/production deployment.
- Keyword-set generation deliberately uses local Ollama (plain HTTP, `requests`) rather than the Anthropic API, so `search` needs no paid API key — this was a direct user decision after finding out a Claude subscription (claude.ai Pro) doesn't grant API access, which is separately billed. `api/routes/papers.py::start_search()` checks reachability eagerly (`check_ollama_reachable`, a 503 before the job is even created) rather than letting a doomed job start and fail a few seconds later.
- The chatbot also runs on Ollama now (`chatbot/agent.py`'s `ChatOllama`, same model/server as `search`) — `ANTHROPIC_API_KEY`/`langchain-anthropic` were removed from the project entirely, not just made optional. There is now no paid API key anywhere in this project; only a running local Ollama with `OLLAMA_MODEL` pulled.
