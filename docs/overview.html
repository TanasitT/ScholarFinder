ScholarFinder project overview

Finding qualified peer reviewers, by rule, not by vibe

Give it a paper's title, abstract, and keywords. It searches the scholarly graph for candidates, applies a fixed set of eligibility rules with no exceptions, scrapes for a contact email without ever guessing one, and keeps every decision — including the rejections — on record.

How a search runs

The batch search pipeline

Eight stages, run in order every time reviewerfinder search is called. Click any stage to see what it does and which file owns it.

InputTitle, abstract, keywords → a new dated search run▸

A title (required), abstract, and comma-separated keywords are submitted via the CLI — or, later, by the chatbot re-running a search on an existing paper. This creates a new papers row stamped with today's date, since the schema models each search as its own dated run rather than mutating a paper record in place.

pipeline.py :: run_search()
Candidate discoveryWho else writes about this?▸

Searches OpenAlex's /works endpoint for papers matching the title/abstract/keywords, then collects the unique set of author IDs who wrote them. This is topic search, not name search — OpenAlex's author endpoint only matches by name, so relevant authors have to be found through their papers instead.

discovery/candidate_finder.py
EnrichmentBuilding a full profile per candidate▸

Each candidate's full OpenAlex author record is fetched — h-index, recent-paper counts by year, current institution, country, ORCID — then cross-checked against Semantic Scholar for a second h-index reading and a homepage URL, kept as a fallback lead for the email hunt later.

discovery/enrichment.py
Core-rule filteringZone, institution, output, h-index — email not yet checked▸

Four of the five hard rules are evaluated here: country trust-zone, academic-only employer, 8+ papers in the last 5 years, and the zone-dependent h-index bar. Candidates are checked against every rule, not just the first failure, so a rejection's full reasoning is captured at once.

passes → sent to email hunt fails → recorded with reasons, dropped before any scraping
rules/filters.py :: passes_all_hard_rules(check_email=False)
Email huntScraped, never guessed▸

For core-rule passers only. Each scholar's most recent open-access papers are fetched and scanned for an email — HTML landing pages directly, PDF-only papers via text extraction. If nothing turns up, their Semantic Scholar homepage is tried as a fallback. No address is ever constructed from a name-and-institution-domain guess.

discovery/email_hunter.py
Final filteringSame rules, email now required▸

The same rule check runs again, this time requiring a discovered email too.

passes → ranked and shown fails (usually: no email found) → recorded, excluded from output
rules/filters.py :: passes_all_hard_rules(check_email=True)
RankingOrdering only — never a filter▸

Scholars who passed every rule are ordered by how closely their research topics overlap the paper's own title/abstract/keywords. This score never removes anyone — it only decides who's shown first.

rules/ranking.py
Persist & outputEvery candidate stays on record▸

Every evaluated scholar — pass or fail — is written to SQLite along with the specific reasons, so a rejection can be explained later instead of just vanishing. The ranked passers are printed: name, institution, h-index, email, topics, and a Google Scholar / Scopus search link for manual identity confirmation.

What "qualified" means

Eligibility rules

Enforced entirely in Python — never by the chatbot's own judgment.

  • ✓8+ papers in the last 5 yearsrecency, not just lifetime output
  • ✓Zone 1 or Zone 2 countryZone 3 and any unlisted country default to excluded
  • ✗Egypt & Saudi Arabia — always excludedhardcoded override; wins even if listed under an allowed zone
  • ✓Academic institution onlynot currently employed by a company
  • ✓H-index ≥ 5 (Zone 1) or ≥ 10 (Zone 2)threshold scales with country trust zone
  • ✓A discovered email addressscraped only — never constructed or guessed
