How a request moves through the system

Two entry points — the CLI and the web UI — feed the same pipeline, rule engine, and SQLite store. Eligibility is decided by pure Python, never an LLM; a local Ollama model only ever decides what gets searched for. The diagrams below trace the actual control flow, including every decision point and rejection path.

Where it's stored

Data model

SQLite (data/reviewerfinder.db) — filtering/staleness/join queries are inherently relational, and a single file needs no extra service to run.

papersone row per submitted search

  • idpk
  • title, abstracttext
  • keywords_jsontext
  • run_datetext

keyword_sets5 rows per paper — one per search angle

  • idpk
  • paper_idfk
  • keywords_jsontext (3 keywords)
→ papers.id

scholarsone row per candidate, keyed by OpenAlex ID

  • idpk (OpenAlex id)
  • display_name, orcidtext
  • h_index, works_count_last_5yint
  • current_institution_*, zonetext
  • email, email_verification_statustext
  • last_checked_attext

paper_scholar_matchesevery evaluated candidate, pass or fail

  • paper_id, keyword_set_id, scholar_idfk (unique)
  • relevance_scorereal
  • passed_hard_rulesbool
  • fail_reasons_jsontext
  • rank_positionint
→ papers.id, keyword_sets.id, scholars.id
What "qualified" means

Eligibility rules

Enforced entirely in Python (rules/filters.py, rules/zones.py) — the two decision diamonds in the pipeline above check exactly these.

  • ✓8+ papers in the last 5 yearsrecency, not just lifetime output
  • ✓Zone 1 or Zone 2 countryZone 3 and any unlisted country default to excluded
  • ✗Egypt & Saudi Arabia — always excludedhardcoded override; wins even if listed under an allowed zone
  • ✓Academic institution onlynot currently employed by a company
  • ✓H-index ≥ 5 (Zone 1) or ≥ 10 (Zone 2)threshold scales with country trust zone
  • ✓A discovered email addressscraped only — never constructed or guessed
