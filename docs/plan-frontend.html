Bringing search + browse to the browser

The CLI stays as-is. This plan adds a FastAPI layer over the existing pipeline and repositories, and a React + Vite app in front of it — nothing about the eligibility rules, discovery pipeline, or database changes.

Scope

Search + browse only. New-search form, past-papers list, paper detail with ranked matches, scholar detail. The chatbot stays CLI-only for now.

Stack

React + Vite frontend, talking to a new FastAPI backend. A real SPA with routing and component state, not a static page.

Spend gate

Running a new search asks for explicit confirmation first, since it spends OpenAlex API budget — same soft-gate as the chatbot's search_new_candidates.

Where the new pieces sit

Everything outlined in blue is new. The pipeline, rule engine, and database are untouched — the API layer just calls them.

Part A — Backend API

A thin FastAPI layer. Paper and Scholar are reused directly as response models — only a few request/list shapes are new.

New endpointsbackend/src/reviewerfinder/api/routes/▸
MethodPathReturns
GET/api/paperslist[PaperSummary] — newest first
GET/api/papers/{paper_id}paper detail + ranked matches (404 if missing)
POST/api/papers/searchruns the real pipeline → SearchResponse
GET/api/scholars/{scholar_id}full Scholar (404 if missing)

POST /api/papers/search is a plain def, not async def — FastAPI runs it in its threadpool automatically, which matters because the pipeline's requests calls are all blocking.

New fileswhat gets created, and why▸
  • api/app.py

    Creates the FastAPI app; startup hook runs init_db() and builds one shared OpenAlex/Semantic Scholar client pair on app.state, reused across requests. No CORS middleware — the Vite dev proxy keeps everything on one origin.

  • api/deps.py

    Dependency functions handing routes a PaperRepository / ScholarRepository / MatchRepository, and the shared clients.

  • api/schemas.py

    SearchRequest, RankedScholar, SearchResponse, PaperSummary — the shapes not already covered by models.py.

  • api/routes/papers.py · scholars.py

    The four endpoints above.

Small additions to existing fileseverything else is reused as-is▸
  • db/repository.py :: PaperRepository.list_all()

    Mirrors ScholarRepository.list_all(), already added in Phase 3.

  • db/repository.py :: MatchRepository.passing_count()

    One small aggregate query per paper, used to build the papers list view. Fine as N+1 at this project's personal/local scale.

  • cli.py :: serve

    New command, same shape as search/refresh/chat — runs uvicorn.run(...) on 127.0.0.1:8000.

  • pyproject.toml

    New optional group: api = [fastapi, uvicorn[standard]].

Part B — Frontend

frontend/ goes from a placeholder README to a real Vite + React app, dev-server only for this pass.

Four pagessrc/pages/▸
  • SearchPage — new-search form. Submitting shows an inline confirm banner before it actually calls the API (the spend gate), then a loading state, then the ranked results with a link to the new paper's detail page.

    Uses POST /api/papers/search

  • PapersPage — past papers: title, run date, passing count.

    Uses GET /api/papers

  • PaperDetailPage — one paper's title/abstract/keywords plus its ranked scholar cards.

    Uses GET /api/papers/{id}

  • ScholarDetailPage — full profile: institution, zone, h-index, email + verification pill, topics, Google Scholar/Scopus links.

    Uses GET /api/scholars/{id}

Shared pieceskeeping it one design system▸
  • src/components/ScholarCard.jsx

    Same pill/chip visual language as docs/overview.html — semantic color kept separate from the accent, so this doesn't look like a bolted-on second design.

  • src/api.js

    Thin fetch wrappers for the four endpoints — one place to change the base path later.

  • vite.config.js

    Dev server on :5173 with a /api proxy to :8000, so the browser only ever talks to one origin.

Explicitly out of scope

Called out on purpose, not silently skipped.

  • ✕Chatbot in the browser — separate, larger scope (streaming responses, session handling).
  • ✕Production build/serving — this pass is dev-mode only (vite dev + uvicorn --reload side by side).
  • ✕Authentication — matches the project's local single-user posture so far.
  • ✕Frontend automated tests — no test runner exists yet in frontend/; manual verification only, same as chat was.

Testing & verification

  1. 01New test_api_papers.py / test_api_scholars.py, using FastAPI's built-in TestClient against a temp DB — same mocking pattern as test_pipeline_e2e_mocked.py, no live calls.
  2. 02pytest from backend/ — new API tests green alongside the existing 81.
  3. 03Manual: reviewerfinder serve + npm run dev side by side, confirm the papers list, run a real search, confirm the spend-gate prompt appears, confirm results render and link through to scholar detail.
